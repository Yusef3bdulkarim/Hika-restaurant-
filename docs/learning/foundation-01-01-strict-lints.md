# foundation-01-01 — Strict lints

<!-- Written by Claude. Short bullets only. Gemini explains ONLY what is written here + the diff. -->

## Problem
- Default `flutter_lints` lets `dynamic` leak in silently and misses common async bugs. Turning strict rules on now (empty codebase) costs nothing; later it means fixing hundreds of files.

## Assumptions
- No new lint package (breakdown decision 3) — rules hand-picked on top of `flutter_lints` 6.0.0.

## Decisions
| Decision | Alternatives considered | Why this one | Trade-off |
|---|---|---|---|
| `flutter_lints` + hand-picked rules | `very_good_analysis` | No extra dependency; every rule is chosen on purpose and understood | We maintain the list ourselves |
| `strict-casts` / `strict-inference` / `strict-raw-types` | Leave defaults | Hand-written `fromJson` (no codegen) must cast explicitly → type errors caught at analyze time, not at runtime | More explicit `as` casts and type arguments to write |
| Dropped `use_super_parameters` from the plan | Keep it | Already in `lints/recommended` — duplicate | — |
| Dropped `require_trailing_commas` | Keep it | Since Dart 3.7 the "tall" `dart format` adds/removes trailing commas itself; the rule would fight the formatter | Comma placement decided by the formatter, not us |
| Exclude `lib/core/l10n/generated/**` | Analyze it | Generated by `flutter gen-l10n` (task 04); we never edit it | Generated code not linted |

## Thinking steps
1. Read which rules `flutter_lints` + `lints/recommended` already enable (avoid duplicates).
2. Pick analyzer modes that protect the riskiest code we will write by hand: JSON parsing.
3. Add rules by goal: style consistency, immutability/`const`, type safety, async bugs.
4. Remove rules that duplicate or conflict with tooling.
5. Run `dart analyze` + `flutter test` — clean.

## Files
- `analysis_options.yaml` — analyzer strict modes, excludes, extra lint rules grouped by purpose.

## Principles & patterns
- **Fail early (shift-left)** — type and async mistakes reported by the analyzer instead of crashing at runtime — overkill for a throwaway prototype.
- **Explicit over implicit** — `strict-casts` forces visible `as` casts on `dynamic` JSON — overkill when models come from code generation (we don't use it).

## Tests
- None — configuration only. Verified by `dart analyze` (no issues) and the existing test suite still passing.
